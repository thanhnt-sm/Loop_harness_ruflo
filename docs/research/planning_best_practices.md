# AI Agent Planning Phase Best Practices Report

Based on research across production AI agent systems (Devin, Cursor, GitHub Copilot Workspace, OpenAI Agents, and open-source frameworks), here is a comprehensive report on planning phase best practices.

## 1. Plan-then-Execute Pattern

### How Systems Separate Planning from Execution

**Devin's Interactive Planning:**
- Initial Assessment: Rapid codebase search to find relevant files and code snippets
- Detailed Plan: Creates implementation plan with code citations and snippets
- Approval Gate: 30-second default wait for feedback (configurable), "Wait for my approval" option for complex tasks
- Plan includes: Relevant files, key findings, implementation questions, code citations with deep-links

**Cursor's Plan Mode:**
- Activated via Shift+Tab or auto-suggested for complex tasks
- Flow: Clarifying questions → Codebase research → Comprehensive plan → Review/edit → Build
- Plans saved as Markdown files (default: home directory, optional: workspace)
- Best for: Complex features, multi-file changes, unclear requirements, architectural decisions

**GitHub Copilot Workspace:**
- Starts from GitHub Issue or natural language task
- Generates comprehensive plan surfacing relevant code and file changes
- Everything (plan to code) is fully editable
- Includes compute environment (Codespaces) for build/test/validate before PR

**OpenAI Agents SDK:**
- Planner agent: High-capability model (GPT-4 class) produces ordered list of steps
- Executor agent: Cheaper/faster model (GPT-4o-mini) executes each step
- Optional Replanner: Reviews results after each step, revises remaining steps if needed
- Separation reduces cost: expensive model runs once for planning, cheap model for execution

### What the Plan Phase Produces

**Standard Plan Artifacts:**
1. **Ordered step list** - Each step is atomic, self-contained with inputs/outputs
2. **Requirement coverage matrix** - Maps requirements to implementation tasks
3. **File change list** - Specific files to create/modify with paths
4. **Dependency graph** - Explicit dependencies between steps (DAG for parallelization)
5. **Risk assessment** - Blockers, complexity factors, potential failure points
6. **Code citations** - References to existing code patterns to follow
7. **Acceptance criteria** - Verifiable success conditions per step

**Advanced Plan Artifacts:**
- **Traceability matrix** - Requirements → Plan steps → Implementation artifacts
- **Function/symbol mapping** - Expected exported functions per requirement
- **Architecture Decision Records (ADRs)** - Documented design choices with rationale
- **Test strategy** - Test cases per requirement/step
- **Rollback plan** - How to undo changes if execution fails

## 3. Plan Quality Criteria

### Evaluation Frameworks

**Agent GPA Framework (Goal-Plan-Action):**
1. **Goal Fulfillment** - Final outcomes match stated goals
2. **Logical Consistency** - Actions consistent with prior actions
3. **Execution Efficiency** - Most efficient path to goal
4. **Plan Quality** - Plan aligned with goals
5. **Plan Adherence** - Actions aligned with plan

**DeepEval Plan Quality Metric (8 parameters):**
- Completeness: All necessary steps included
- Executability: Each step is actionable
- Optimality: No unnecessary steps
- Dependency correctness: Dependencies are valid
- Risk awareness: High-risk steps identified
- Fallback coverage: Failure paths planned
- Resource sufficiency: Required tools/data available
- Verifiability: Success conditions are testable

**Plan-Build-Run 10-Dimension Check:**
- D1: Requirement Coverage (all must-haves have tasks)
- D2: Task Completeness (tasks are atomic and actionable)
- D3: Dependency Correctness (acyclic, targets exist)
- D4: Key Links Planned (all key links have implementation)
- D5: Scope Sanity (no scope creep)
- D6: Must-Haves Derivation (verifiable, not runtime-only)
- D7: Context Compliance (follows CLAUDE.md/AGENTS.md)
- D8: Risk Assessment (blockers identified)
- D9: Test Coverage (acceptance criteria defined)
- D10: Rollback Plan (undo strategy documented)

### Completeness Checks

**Pre-Execution Checklist:**
```
□ All requirements from spec have corresponding plan tasks
□ Every plan task traces back to a requirement (no orphan tasks)
□ Dependencies are explicit and acyclic
□ File paths are concrete (not "create authentication module")
□ Function/symbol names specified per requirement
□ Acceptance criteria are falsifiable and testable
□ Risk assessment includes blockers and mitigation
□ Rollback procedure is defined
□ Test cases cover happy path and edge cases
□ Security/compliance considerations documented
□ ADRs capture all non-trivial decisions
□ Plan fits within context window limits
```

## 4. Documentation as Source of Truth

### Contract-Based Documentation

**AGENTS.md Pattern (Agents First Principle):**
- Lives at repository root
- First file every agent reads
- Defines permissions, sequences, formatting requirements
- Tool definitions say what's possible; contract says what's allowed
- Example: "Never call delete_record without first calling find_dependencies"

**AgentContract Specification:**
- YAML document declaring behavioral boundaries
- Three obligation types: `must`, `must_not`, `can`
- Quantitative limits and named assertions
- Enforcement policies: warn, block, rollback, halt_and_alert
- Runtime validation on every run

**AID (Agent Interface Documentation):**
- Token-efficient format designed for AI agents
- Complete type signatures, error conditions, parameter constraints
- Workflow blocks describing API sequences
- Zero prose - every piece of information in named fields
- Agentic dataflow (graphs, cycles, state channels, tools, agents)

### Enforcement Mechanisms

**Plan-to-Contract Validation:**
1. Parse AGENTS.md/contract.yaml at plan generation
2. Check each planned step against contract clauses
3. Flag violations before execution begins
4. Require plan revision if contract violated

**Runtime Enforcement:**
- Guardrails validate input/output/tool behavior automatically
- Policy layer returns: allow, deny, or approval_required
- Certified traces: execution only proceeds with valid certificate
- Permissibility Machine validates proposed trace against policy

**Post-Execution Audit:**
- MTM Contract: audit clauses after implementation ships
- Mark each clause: PASS, FAIL, or MUTATED with reason
- Close loop between declared intent and observable outcome
- Traceability matrix links plan items to executed code

### Compliance Verification

**Automated Checks:**
```python
# Example compliance check
def verify_plan_compliance(plan, contract):
    violations = []
    for step in plan.steps:
        for clause in contract.must:
            if not clause.satisfied_by(step):
                violations.append({
                    'step': step.id,
                    'clause': clause.id,
                    'severity': clause.severity
                })
    return violations
```

**Traceability Verification:**
- Requirement → Plan step → Implementation file → Function/symbol

## 5. Human Approval Gates

### Approval Gate Design

**OpenAI Agents SDK Pattern:**
- Tools declare `needsApproval: true` or async function
- Run pauses, returns `interruptions` array
- Resolve via `result.state.approve(interruption)` or `reject(interruption)`
- Works across nested agent.asTool() calls
- Same interruption pattern at all nesting levels

**Airbyte's Four-Component Architecture:**
1. **Confidence Threshold** - Determines if agent should pause
2. **Async Queue** - Holds approval decision
3. **Timeout** - How long agent waits before proceeding
4. **Durable State** - Survives deploy restarts

**Implementation Order (Critical):**
1. Durable state first (prevents state loss on deploy)
2. Async queue (handles multiple pending approvals)
3. Timeout (prevents indefinite hangs)
4. Confidence threshold (reduces unnecessary pauses)

### Approval Presentation Format

**Standard Approval Request:**
```markdown

**Action:** [tool name with description]
**Risk Tier:** R1/R2/R3/R4
**Confidence:** [0-1 score]

### Proposed Change
- File: [path]
- Operation: [create/modify/delete]
- Diff: [snippet or link]

### Justification
- Why this action is needed
- Alternatives considered

- Estimated impact: [description]

- [ ] Approve

```

**Approval Request Context Requirements:**
- Preview of change (diff, arguments, expected output)
- Reason for action (why agent chose this)
- Policy context (which rule triggered approval)
- Hash of arguments for verification
- TTL and cancellation info

### Approval Scope Configuration

**Risk-Based Approval Tiers:**
| Action Type | Default Policy | Override |
|-------------|-----------------|----------|
| Read operations | Auto-approve | N/A |
| Write to dev/staging | Auto-approve | Require approval |
| Write to production | approval_required | Configurable |
| Data deletion | approval_required | Always require |
| External API calls | approval_required | Per-allowlist |
| PII access | approval_required | Always require |

**Approval Lifecycle:**
1. Tool invocation about to execute
2. Policy evaluates approval rule
3. If required and no decision: record RunToolApprovalItem
4. Run pauses, returns pending approvals in `interruptions`
5. Human resolves: approve, reject, or approve with modifications
6. Execute tool if approved, skip if rejected
7. Log decision to audit trail

**Coverage Metrics:**

- Test coverage: % of requirements with acceptance tests

**Gap Detection:**
```python
# Example gap analysis
def detect_coverage_gaps(plan, implementation):
    gaps = []
    for req in plan.requirements:
        if not req.has_implementation():
            gaps.append({
                'type': 'requirement',
                'id': req.id,
                'severity': 'BLOCKER' if req.priority == 'P0' else 'WARNING'
            })
    for task in plan.tasks:
        if not task.has_code():
            gaps.append({
                'type': 'task',
                'id': task.id,
                'severity': 'BLOCKER'
            })
    return gaps
```

## 10-15 Best Practices for Planning Phases

### Planning Process

1. **Separate Planning from Execution**
   - Use Plan-then-Execute pattern for all non-trivial tasks
   - Planner: strong model (GPT-4/Claude Sonnet) for strategic decomposition
   - Executor: cheaper model (GPT-4o-mini/Claude Haiku) for tactical execution
   - Reduces cost 3-4x and improves predictability

2. **Generate Plans Before Any Code Changes**
   - Never allow agents to modify files without an approved plan
   - Plan must include: file paths, function names, dependencies, acceptance criteria
   - Use slash commands like `/plan` (Devin, Cursor) to enforce planning phase

3. **Make Plans Inspectable and Editable**
   - Plans as Markdown files in workspace (not hidden in chat)
   - Include code citations with deep-links to verify context
   - Allow inline editing before execution
   - Version control plans alongside code

4. **Require Clarifying Questions**
   - Agent must ask questions before generating plan for ambiguous tasks
   - Prevent two-word answers that lead to wrong-direction research
   - Document answers in plan for traceability

5. **Use Dependency Graphs for Complex Tasks**
   - Represent plan as DAG, not just linear list
   - Enable parallel execution of independent steps
   - Explicit dependency tracking prevents ordering errors

### Plan Quality

6. **Enforce Requirement Coverage**
   - Every requirement from spec must have at least one plan task
   - Every plan task must trace back to a requirement (no orphans)
   - Use coverage matrix with 4 columns: Requirement, Description, File Path, Function/Symbol
   - Calculate coverage percentage; block execution below threshold

7. **Make Steps Atomic and Verifiable**
   - Each step: one clear action with defined inputs/outputs
   - Acceptance criteria must be falsifiable (testable)
   - Avoid vague steps like "improve performance"
   - Specify concrete functions, files, entities

8. **Include Risk Assessment**
   - Identify blockers, dependencies, complexity factors
   - Classify risk tier (R0-R4) with approval requirements
   - Document mitigation strategies for high-risk steps
   - Include rollback procedure for reversible changes

9. **Document Architecture Decisions**
   - Capture non-trivial choices as ADRs
   - Each ADR: decision, choice, rationale, trade-offs, status
   - Require human confirmation for each ADR
   - Link ADRs to plan steps that implement them

10. **Specify Test Strategy**
    - Define acceptance tests per requirement
    - Include unit, integration, E2E test cases
    - Specify test data and edge cases
    - Plan for test execution before deployment

### Documentation as Contract

11. **Maintain AGENTS.md as Contract**
    - Single source of truth for agent behavior rules
    - Define permissions, sequences, formatting requirements
    - Tool definitions = possible; contract = allowed
    - Load as first file in every agent session

12. **Use Structured Documentation Formats**
    - AID (Agent Interface Documentation) for API contracts
    - AgentContract YAML for behavioral boundaries
    - Zero prose - every fact in named fields
    - Token-efficient for agent consumption

13. **Enforce Contract Compliance**
    - Validate plan against contract before execution
    - Runtime guardrails for input/output/tool behavior
    - Post-execution audit: mark clauses PASS/FAIL/MUTATED
    - Block execution if contract violations detected

### Approval and Traceability

14. **Implement Risk-Based Approval Gates**
    - Auto-approve low-risk (R0) routine changes
    - Plan review for moderate complexity (R1)
    - ADR review for high complexity (R2)
    - Full architecture review for critical/regulatory (R3-R4)
    - Use durable state + async queue + timeout + confidence threshold

15. **Maintain End-to-End Traceability**
    - Requirement → Plan step → Implementation file → Function → Test
    - Generate traceability matrix during Plan phase
    - Pass matrix to Developer for self-verification
    - Phase review: verify expected files/symbols exist
    - QC: re-verify authoritatively against implementation
    - Log execution provenance: operational + cognitive + contextual

```python
def validate_plan_before_execution(plan):
    checks = {
```

### Runtime Enforcement

1. **Plan-Based Execution**
   - Executor receives plan as structured object
   - Must execute steps in order (respect dependencies)
   - Cannot deviate without raising replan request
   - Log each step completion with trace ID

2. **Symbol Verification**
   - After each step, grep for expected symbols
   - Mark step complete only if symbols found
   - Flag missing symbols as execution gap
   - Require human approval to continue if gaps

3. **Contract Guardrails**
   - Before each tool call, check against contract
   - Block calls violating `must_not` clauses
   - Require approval for calls not in `can` clauses
   - Log all contract checks

### Post-Execution Verification

```python
def verify_execution_compliance(plan, execution_trace):
    compliance = {
```

## Summary

The planning phase is the critical control point in AI agent systems. Production-grade systems (Devin, Cursor, GitHub Copilot Workspace, OpenAI Agents) all separate planning from execution using the Plan-then-Execute pattern. Key success factors include:

1. **Structured plans** with requirement coverage, file paths, function names, and acceptance criteria
2. **Quality gates** with pre-execution validation, risk assessment, and completeness checks
3. **Contract-based documentation** (AGENTS.md, AgentContract, AID) that defines behavioral boundaries
4. **Risk-based approval** with tiered gates, durable state, and proper timeout handling
5. **End-to-end traceability** from requirements through plan to implementation to tests

The most effective systems treat the plan as a contract that binds execution, enforce compliance through automated checks and human approval gates, and maintain traceability throughout the lifecycle to ensure the agent delivers what was promised.
